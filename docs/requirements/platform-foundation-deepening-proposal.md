## 3 为什么优先任务中心

当前导入、导出、分析、图模转换和大屏包校验已经产生后台工作，用户需要在离开原页面后查看进展及结果。站内通知补齐“发生了什么、需要去哪里查看”，任务中心补齐“还在做什么、能做什么、结果是否仍可用”。两者复用同一业务引用和执行代次，形成互相可到达的入口。

先接入这些真实任务，可以验证公共契约是否足够，而无需等待设备、协议或新监测业务。后续文件处理、备份、报告等按明确契约接入；尚未实施的业务不列入本轮适配验收。

本轮深化任务的公共访问和管理能力。通用定时计划、批量编排和执行资源调度仍属于更完整任务平台的后续范围，本轮完成不代表方案中全部调度能力已交付。

### 4.1 对象及状态

人员操作、业务运行、执行尝试和内部子任务分别表达。同一业务运行的内部重试保留原身份，人工重试按所属模块规则形成可追溯的新执行代次，不能覆盖既有失败依据。业务需要用户继续采用或发布时，页面明确显示下一步。

发起人只是任务事实之一，不自动成为永久运行身份或结果读取凭证。后台任务使用原领域执行资格或持久委托；大屏 ReadSubject、终端以及通知投递身份不伪装为人员账号。

未知进度显示阶段或已完成工作量，不生成虚假的百分比。来源暂不可查询时显示状态待核实及最后核实时间，不把它直接改成失败、已取消或完成。

### 4.2 接入与执行边界

已有队列及状态由所属模块继续拥有。公共模块通过有限 Adapter 查询、鉴权和执行控制；取消请求先显示已请求，实际终止、发布隔离和清理仍按原任务机制完成。重试先检查固定输入、当前权限和目标版本，不能用统一按钮绕过业务校验。

可建立可恢复的公共任务索引用于筛选和定位，记录来源版本及最后同步情况；任务事实和可执行动作由来源复核。同步使用持久交接与幂等处理，不能只靠内存广播。详细设计须固定每个来源的初始纳入、增量更新和恢复策略。

列表、计数和筛选项均按当前授权生成，不先对全实例分页再隐藏无权条目，也不让聚合泄漏他人的工作。我的任务与管理视图使用各自明确的读取资格；无权访问原结果时不从公共索引取出原结果正文。

大屏包处理进程保留原有最小权限。通过领域自有交接及受控适配器传递有限状态，不给受限 worker 增加账号、全局任务、全局通知或其他业务表的访问权限。

### 4.3 与通知的职责

任务中心读取当前任务事实；通知箱保存发给人员的事件回执和阅读状态。通知已投递不表示任务结果已被业务采用，任务已完成也不代表通知已经送达。

任务中心不根据列表状态变化另行广播完成消息。沿用正在实施的通知方案，由真正提交业务终态的路径生成一次事实；现有来源键、接收人快照和资格检查继续适用。通知投递暂停时，任务执行和查询仍按各自依赖工作，通知恢复后按原事实补投。

自动重试属于同一执行过程，不为中间失败逐次通知。人工明确重试后的新执行代次可以按原通知规则产生新的结果回执；同一代次的结果不重复投递。旧通知保留当时的结果含义，进入任务后能区分对应代次与当前最新状态。账号、角色和邀请等通知继续进入其自身业务页面。

### 4.4 已确认的默认视图和管理原则

以下两项由用户在本轮讨论中明确选择，其余细化内容为建议方案。

| 已确认事项 | 产品行为 |
| --- | --- |
| 默认我的全部任务 | 默认汇总本人在不同租户、项目中发起且当前仍有权查看的任务；提供“当前工作空间”快捷筛选及租户、项目筛选。切换工作空间不把默认视图自动改成单项目列表。 |
| 按业务权限管理他人任务 | 管理视图只汇总当前获准管理的任务类型与范围；支持的取消、重试操作可由管理人员执行，并保存操作人、理由、时间和执行代次。 |

“我的”是任务筛选条件，不是永久授权。失去原业务资格后，任务名称、计数、详情和结果按同一可见性规则收回。平台管理员身份也不自动获得全部租户任务正文或业务数据。

查看任务、管理任务、读取结果和下载文件分别核验。管理人员可以在获得任务管理权但没有结果读取权时执行获准控制；此时页面只展示允许的任务摘要，不暴露输入、敏感错误或结果内容。任务管理权不等于绕过执行所需的数据权限。

### 4.5 页面与操作预期

建议沿用现有控制台布局、表格、侧面板、语义颜色及响应式组件，采用全局入口和业务内快捷入口。

| 页面或入口 | 用户看到什么 | 用户可以做什么 |
| --- | --- | --- |
| 全局任务入口 | 与通知入口相邻，可查看本人正在进行的工作摘要。 | 打开任务中心；完成消息仍由通知铃铛提示。 |
| 我的任务 | 进行中、需处理和已结束的快捷筛选；任务名称、业务类型、租户／项目、阶段、提交与更新时间、结果状态。 | 按范围、类型、状态和时间筛选，按名称或编号检索，分页查阅历史。 |
| 管理视图 | 获准范围内的任务，增加发起人和人工／自动来源筛选。 | 查看他人任务；按返回的可用操作管理，读取结果仍单独核验。 |
| 任务详情 | 概况、阶段进度、执行记录、中文错误解释、结果和下一步；高级区域展示错误码和排障关联号。 | 请求取消、条件允许时重试、查看批次或成果、下载获准文件；可用链接定位到固定任务和执行代次。 |
| 原业务页面 | 当前业务的任务状态和相关任务列表。 | 继续从导入、分析、图模、大屏页面发起工作，进入统一任务详情；业务参数、采用和发布仍在原页面完成。 |

桌面列表点击后打开详情侧面板，详情支持直接链接和刷新恢复；窄屏使用全屏详情。状态同时用文字和图形表示，筛选、列表和操作支持键盘。原“监测任务”入口复用统一任务视图并预置业务范围，“计算运行”保留固定输入、来源和成果等专业信息，避免维护两套进度与取消界面。

任务页打开时建议每 3 秒更新活动任务，页面隐藏时暂停轮询，回到页面后立即核对；终态任务减少刷新。刷新失败保留最后确认状态和确认时间，并提示暂未更新。已知总量时显示完成数和比例，未知总量时显示真实阶段与已处理量。

后台执行和业务结果分别表达。例如：

| 工作 | 执行情况 | 结果与下一步 |
| --- | --- | --- |
| 导入校验 | 校验完成 | 展示错误或可采用情况；用户到批次页面明确采用。 |
| 数据导出 | 导出完成 | 文件可下载并标明有效期；过期后保留执行记录，按当前范围重新申请。 |
| 空间转换 | 转换完成 | 资料处于草稿，进入图模管理检查、挂载并发布。 |
| 大屏包处理 | 包校验通过 | 包可以用于配置与发布，实际运行版本由大屏管理页面决定。 |
| 历史分析 | 计算完成 | 进入固定成果；后续输入变化时显示成果模块给出的影响说明。 |

状态快捷分组建议为“进行中”“需处理”“已结束”。“需处理”包括最终失败和来源明确要求人工介入的情况；等待上游、等待自动重试仍属于进行中。采用或发布入口可作为成功任务的下一步提示，不据此新增人工审批或待办机制。

| 监测查询与导出 | 数据导出，以及已持久化并转入后台的耗时精确查询。 | 允许时取消；导出文件复用原下载检查。快查询不另造任务；过期快照通过原业务重新申请。 |
| 派生监测 | 已持久化的试算、人工回算、历史修正、原依据回放及派生依据导出。 | 固定原输入与配置，显示上游等待和子任务关系；按原规则取消或重试，不在重试时偷偷替换输入。 |
| 历史分析 | 试算、正式运行、成果比较、成果导出。 | 关联原配置与固定成果；失败、重试和重算记录可追溯，正式重算仍由业务页面发起。 |

多个内部任务服务于同一次用户操作时，人员列表优先展示业务运行，详情展开依赖任务和尝试记录。聚合数量和阶段来自真实来源，不凭内部任务行数估算整体百分比。

文件尚在浏览器上传时继续显示原上传进度；只有服务端接收并建立后台任务后，才能承诺离开页面仍继续执行。旧任务按仍保留的来源记录纳入，原来没有保存的逐次尝试记录明确标为历史明细不可用，不推测补造。

### 4.7 管理操作与执行身份

当前[监测任务查询和授权](/Users/hijacker/Documents/ChatGPT/InfraPro/packages/go/platform/monitoring/jobs.go)主要按空间与发起人限制，[计算运行控制](/Users/hijacker/Documents/ChatGPT/InfraPro/packages/go/platform/derivedmonitoring/runs.go)还复核原运行资格。跨空间查询及管理他人任务需要在各所属模块补齐明确的查询和控制接口，并接入现有角色权限体系，不能只在前端去掉发起人筛选。

建议遵守以下操作规则：

1. 取消操作说明对象、当前阶段和影响；管理他人任务须填写理由。提交后显示“取消已请求”，来源已完成终态迁移时显示“已取消”。执行进程后续清理不应再发布有效结果；与完成竞争时以来源实际结果为准。
2. 重试前复核当前管理权、原固定输入、目标版本和执行资格。适合原任务重试时保留业务任务身份并增加执行代次；必须重新选择范围、重新上传或改配置时，回到原业务创建新任务，并关联原失败记录。
3. 原始发起人、本次操作人和实际执行主体分别记录。管理员重试不自动冒用原人员身份；各来源继续明确使用原有效资格、合法委托，或经业务命令明确建立本次新运行资格。来源不支持资格转换时拒绝直接重试，并提供合法重建入口。
4. 人工重试不能清掉前一次失败和操作记录。当前部分来源会重置尝试计数或错误字段，接入时须在同一状态迁移事务保存前代执行记录，再开始下一代。来源已有租约隔离和旧执行防覆盖机制继续生效。
5. 操作成功后由来源返回最新状态和修订；重复点击、多个管理员同时操作、使用旧页面提交都须有幂等和版本冲突处理。列表按钮与后端检查使用同一可用操作判断。

## 5 技术及实施方式

| 技术／模块 | 本轮用途 |
| --- | --- |
| Go 领域接口与 runtime 装配 | 建立任务注册、类型化查询和动作契约，装配监测、分析、空间及大屏适配器；业务状态机仍由各领域拥有。 |
| PostgreSQL | 沿用持久任务、租约和执行代次；按需增加任务索引、交接及接入版本。不以缓存代替事实。 |
| React／TypeScript 与现有 API client | 任务中心、筛选、详情和结果入口；复用现有取消请求、会话失效处理及查询缓存。 |
| 已有通知接口 | 复用事件键和业务引用，完成通知与任务导航。 |
| 已有文件读取及下载接口 | 结果按当前权限读取，不将私有对象地址放入通知或任务索引。 |
| 现有 worker 和运维命令 | 保留原执行隔离、重试及恢复；补充任务接入诊断。 |

本轮沿用现有技术栈。Go 承担类型注册、查询、权限与操作适配；PostgreSQL 保存跨模块任务索引、持久交接和执行记录；React、TypeScript、TanStack Query／Router 承担统一页面、轮询、缓存清理与深链接。实际计算、转换和包处理继续由各自 worker 执行，结果载荷继续使用原存储和下载接口。

建议新增独立的公共任务模块，集中处理跨空间分页、状态展示、执行记录和结果导航。各来源通过小型适配接口提供任务身份、范围、当前状态、读取资格、允许的操作及业务结果引用；详细计算参数和业务状态机保留在所属模块。未来模块按类型注册、状态接入、授权与动作适配、结果链接和契约测试接入。

公共索引用于检索和定位，不成为第二个执行队列。普通来源在业务事务内登记或留下持久变更记录；大屏通过自身交接记录同步，包处理 worker 不获得全局任务表权限。同步按来源标识和修订幂等处理，忽略迟到的旧状态；启动和升级时对账补齐。阶段变化可同步，心跳不必逐条变成用户执行记录。

任务创建、进度和终态的同步独立于个人通知投递：关闭通知偏好或停止通知 worker 都不影响任务登记。通知的业务事实用于结果回执关联，不能把通知箱当成任务索引的数据源。当前[任务终结入口](/Users/hijacker/Documents/ChatGPT/InfraPro/packages/go/platform/monitoring/task_completion.go)和[通知目标映射](/Users/hijacker/Documents/ChatGPT/InfraPro/apps/console/src/features/notifications/targets.ts)是联动的实际接入点；旧通知目标仍须可解析到原业务或固定任务代次。

跨空间列表在授权后形成分页、计数和筛选候选，来源模块负责批量资格判断；不能简单合并各模块第一页或先分页再丢弃无权条目。详情、控制与下载再次按来源复核，源暂不可用时返回最后确认状态及不可执行原因。历史回填可中断恢复并与增量同步对账，不凭单一最大 ID 判断所有旧事务都已提交。

内部实施按“契约与接入矩阵 → 查询和操作接口 → 全部已列来源适配 → 控制台与通知联调 → 故障及权限回归”推进。通知模块的最终接口是联调依赖；准备契约不需要中断其当前实施，接入时以其完成代码为准。

## 6 可观察的验收条件

1. 从原业务页面发起导出、历史分析、空间转换及大屏包校验后，统一任务中心显示各自正确范围、人员、阶段和结果；离开页面或重新登录后仍能查到。
2. 从任务进入原批次、成果或文件；执行成功但尚未采用／发布时，页面明确区分。撤权后无法从任务或通知绕过原结果权限。
3. 在允许取消的任务上发起取消，状态如实反映实际停止；在允许重试的失败任务上重试，保留原失败依据和新执行代次，旧尝试不能覆盖新结果。
4. 通知和任务引用一致，完成消息不因多处页面或索引同步重复产生；阅读、归档通知不改变任务。
5. 两个项目及不同成员的任务、计数、结果和可用操作正确隔离；运维诊断权限不自动授予业务文件读取权。
6. 重启、重复交接、来源暂不可用及索引恢复后，任务可核对且不重复执行；纳入历史任务不会重新通知或自动重跑。
7. 同一账号在两个租户、多个项目发起任务，默认“我的任务”能够汇总；筛选当前项目后只显示该范围，计数、翻页及详情与当前授权一致。
8. 管理人员对他人任务执行获准取消或重试，发起人、管理操作人和执行代次分别可追溯；只有任务管理权时，仍不能下载无权读取的结果。
9. 人工重试后旧失败记录仍可查；关闭通知偏好或停止通知 worker 不影响任务进度，自动重试不制造重复回执；旧通知能解释当时结果。
10. 多任务和等待上游场景显示真实阶段；桌面、窄屏、键盘、刷新失败及账号切换可用。交付合成账号、任务和预期结果，用户无需准备真实设备、模型或协议。
