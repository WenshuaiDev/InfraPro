# 派生监测与历史分析使用、维护说明

## 入口和准备

登录后进入有权访问的租户或项目工作空间，在监测区域使用“派生指标”“派生通道”“历史分析”“计算运行”。派生指标定义由租户维护；项目使用已发布版本。直接监测通道仍按[监测数据说明](monitoring-data.md)导入原始文件。派生通道不能绑定设备通道或接收原始文件导入。

开始前准备设施、构件或测点归属，以及已经正式发布的原始输入。项目身份还需要通道资源授权和对应时间范围的数据授权。配置管理权限不等于数据读取、历史或导出权限。输入存在于其他项目，不会自动使本项目可以使用；项目成果只属于创建它的项目。

缺少输入时可先建档。试算会明确显示没有输入；启用时必须明确选择等待输入。系统不会把无样本改成零值，也不会把未完成的计算显示成已有监测值。

## 定义指标并发布

1. 打开“派生指标”，创建草稿，填写唯一编码、名称和用途。选择输入量纲、固定单位、时间含义、方向、基准以及允许的原始／派生来源。具有物理单位的值不能与无量纲数或不同时间聚合语义混用。
2. 选择常用模板，或编辑步骤。模板会替换当前步骤，之后仍可编辑。步骤引用输入槽或此前步骤；公式只能使用界面支持的变量和算术表达式，不能调用任意脚本、网络或数据库。
3. 指定输出语义及小数位数。计算过程采用精确数值契约，最终结果采用 half-even 舍入；输出位数决定保存的规范值。改名称不会重新解释既有值；改变单位、方向、基准或结果含义需要按语义变更流程处理。
4. 保存草稿，点击“校验已保存草稿”。错误显示具体字段或步骤，点击错误位置可返回修正。修改后重新保存、校验；旧校验收据不能发布新草稿。
5. 点击“发布固定版本”。新建通道选择明确的发布版本。停用定义会阻止新的使用，已有固定配置和历史依据仍保留。需要独立演进时使用复制，复制后单独保存和发布。

## 建立通道、试算和启用

1. 在“派生通道”新建，或从设施／构件／测点详情的新建派生通道入口进入。确认归属、编号、名称及指标版本。设施直属通道、构件直属通道与测点通道都是正式资源。
2. 为每个输入槽选择同租户且语义兼容的通道。输入可以是原始通道，也可以是已经正式计算的派生通道；系统拒绝环和超过八层的依赖。配置中未获得的输入只显示受限状态，不返回原值。
3. 若规则使用固定观测基准，选择准确的观测／采用身份，或上游结果／代次身份；若使用参考窗口，指定完整时间范围和统计方法。固定基准第一次确认后使用原快照，后续追加不会悄悄改变它。撤销原采用会使该基准失效，重新采用产生的新身份不会复活旧基准。
4. 保存后进入“试算固定配置”。填写包含起点、不包含终点的范围；时间可以带时区和纳秒。试算范围需要覆盖实际候选、前驱及基准的授权，而不仅是界面上显示的输出时段。
5. 点击“对完整范围试算”。小任务直接显示结果；超出交互预算时转后台，仍计算完整目标。查看输入行数、输出数、质量／状态计数、实际匹配时刻、节点说明和基准。下方示例有上限，计数覆盖完整任务，不应把示例行数当成总量。
6. 在“启用持续计算”填写自动起点，选择持续生效或明确终点，预览影响，再确认。系统重新核对配置修订、输入范围和有效试算回执。默认试算回执 30 分钟到期，过期后重新试算。

启用采用持久执行委托，后续自动运行不依赖创建者保持登录。项目授权不能覆盖未来时，不能据此开启无限未来输入范围。新数据正式发布后才进入计算；上传或校验中的文件不会触发正式值。

## 查看结果和新鲜度

“监测浏览”可以一起选择原始和派生通道。明细显示准确值、单位、质量、计算状态、样本数和来源身份；趋势与统计使用正式结果，历史修订不混入当前样本。

在“选择监测通道”中，默认“全部对象”列出设施、构件和测点所属通道，可按来源类型、所属对象或名称筛选并勾选；需要原有测点列表时点击“按测点浏览”，再选择测点。手机先打开“测点与通道”面板，选择后点击“查看已选…个通道”返回结果。导入文件的映射选择器只允许直接观测通道，不能将原始文件映射到派生输出。

| 页面情况 | 含义与操作 |
| --- | --- |
| 当前结果 | 当前配置和相关来源已核对，可以作为当前值使用。 |
| 待计算／等待上游 | 所需范围尚未形成完整正式结果。查看计算运行及上游通道，不将空白视作零值。 |
| 无结果、除零、基准失效或输入不足 | 此输出时刻已经计算，规则给出明确的无结果状态。查看原因和原依据。 |
| 最新输出无有效数值 | 最新状态与“上一有效值”分别显示；上一有效值不是最新时刻测得的值。 |
| 输入后来变化 | 原固定成果仍有历史意义；查看变化范围，按当前输入重新运行产生新版本。 |
| 正式载荷／依据不完整 | 对账已确认缺块或损坏，停止返回该结果及依赖它的缓存。由维护人员恢复依据，或通过获准回算发布新代次。 |

自然日／月／年按所选时区解释。趋势抽样用于展示，统计覆盖查询定义的正式样本。不同单位分别查看，数值提示与导出保留精确文本。固定窗口未到期时，系统不会提前将未闭合窗口作为正式结果。

## 暂停、恢复和修改配置

暂停前先预览并确认影响。暂停保留已有结果及尚未完成的变化范围；旧 worker 的执行资格同时失效。资源退役会停止相关持续计算，恢复资源后保持计算暂停，需要明确恢复。

恢复可选择补齐暂停期间，或从新的明确起点继续。新起点不会偷偷补算更早历史；需要早于原自动起点的数据时，使用显式历史回算。预览中过期修订、撤权或配置变化会阻止提交，应重新获取预览。

普通参数调整创建新的固定配置并选择生效范围。历史修正必须明确范围和原因。身份语义发生变化时，按预览要求建立新通道，不能用一个历史身份表达两种含义。不要将规则输出的小数位数与页面显示格式混淆。

## 历史回算、上游依赖和回放

在通道详情的历史回算中填写范围，先预览；查看哪些配置段适用、是否有无配置区间及尚未计算的上游范围。需要补算上游时，明确选择依赖回算。系统建立固定子任务并等待上游完成，后续不会替用户扩大自动起点或改写其他配置。

到“发布历史与原依据”查询一个范围，选择代次。可以查看所选片段的原始快照、上游固定代次、基准、配置和准确结果。部分授权只返回获准片段，不显示整个代次的行数或状态总数。

“按原配置、原来源回放并核对”读取当时的固定采用和上游代次，对比保存结果，报告一致或差异。它不发布为当前。按当前来源重新计算应使用历史回算或重新运行分析；两者的用途不同。

## 历史分析和成果比较

1. 打开“历史分析”新建配置，填写输入绑定、参数和一到十六个输出。分析支持历史 nearest 匹配和 whole_range；这些非因果选择不会成为持续派生通道的自动规则。
2. 保存草稿、校验，再保存固定执行版本。运行时选择该版本、输出范围、输出项及质量；whole_range 还需明确来源范围。整段汇总用来源区间终点标记，结果包含原区间，完整区间查询和导出会保留这一行。
3. 可以先试算，再“运行并生成完整成果”。任务离开页面后继续。多个输出全部完成后才发布成果版本，失败或取消不会留下可冒充完整成果的半成品。
4. 进入固定成果，查看明细、来源、输入变化说明。运行中后续追加不会进入原快照；结果可能标记为截至原快照且已受影响。相关来源撤销会阻止未完成成果发布。
5. 重新运行产生新成果版本，旧版本保留。比较时明确左／右版本和输出对应，查看新增、删除、数值、状态、质量、样本和输入／配置变化。大比较是后台任务，差异可翻页读取，不止有限示例。
6. 归档配置停止新运行，归档成果保留已有版本。项目归档后，获准历史查看和导出保留，修改和新运行停止。

## 导出结果和完整输入依据

在成果详情选择“正式计算结果”或“完整输入依据”，选择 CSV 或 Parquet，填写原因并创建后台任务。派生通道的所选历史代次也提供“后台生成完整输入依据”。离开后在“计算运行”的相应导出列表返回。

结果导出固定输出版本和范围。输入依据导出列出完整获准候选集、质量不合格候选、上游正式结果及其递归来源、固定基准；每行带来源身份、快照和依据路径。候选值未必是最终命中的值，原规则、搜索范围、匹配方式和基准一起保存在下载清单中。多个步骤引用相同来源时，依据路径用来区分用途，不应把这些行当成重复入库。

CSV 精确模式适合程序交换；表格安全模式对可能被软件当作公式的文本作可逆转义。Parquet 的派生数值和依据数值采用精确十进制文本列，另有 scale／rounding，并非 Float64 或 Parquet DECIMAL。时间保留 UTC 纳秒。每卷提供实际行数、字节数和 SHA-256，先下载清单可核对全部卷。

下载默认七天到期。发生相关撤销，旧导出停止下载；确需原依据时重新申请明确的历史导出，并重新核对历史／导出权限。账号、项目、资源或输入权限被撤销后，即使已有下载入口，也不能继续读取后续文件块。正式历史与原始证据不会随下载文件到期删除。

## 任务失败、取消和重试

“计算运行”保留固定目标、范围、追踪编号和状态，任务中心也提供对应入口。取消会传递到读取和计算循环；取消后保留已经正式发布的独立部分，并明确显示状态。技术重试继续原固定目标和检查点，不能把旧固定来源替换成今天的数据。若需要改变配置、范围或来源，创建新运行。

`needs_action` 表示需要处理权限、固定基准、规则预算、临时盘或上游任务等原因。先处理明确原因，再重试。试算过期清理后仍保留运行记录并标记过期；需要查看示例或确认启用时重新试算。

## 配置、启动和维护

API、独立 worker 和 CLI 使用同一份配置及相同版本程序。字段及默认预算见 [infrapro.example.yaml](../../configs/infrapro.example.yaml)。`derived.*` 可通过 `INFRAPRO_DERIVED_<字段大写>` 覆盖；共享租约由 `monitoring_task_lease`、`monitoring_task_heartbeat`、`monitoring_task_attempts` 配置。默认前台、历史任务各保留一个槽位，租户间公平领取。降低并发、增加临时盘或提高部署预算不改变规则的数值语义。

### 新环境

先准备PostgreSQL 17、Redis、一个或多个ClickHouse节点及S3兼容对象存储。单节点可用于首期试运行，不提供数据副本冗余。CH需要与配置名称一致的存储策略、online卷和Keeper；测试用compose见`deploy/monitoring-contract`，其公开凭据仅用于合成测试。复制配置样例到自己的受保护配置文件，填写数据库／Redis、CSRF密钥、前端地址、可信Origin、维护联系人、CH地址与数据库、S3 endpoint／bucket／身份及临时目录。使用本机浏览器时绑定loopback并将`cookie_secure`设为false；实际HTTPS部署按真实入口配置。

从仓库根目录，在同一套配置下依次执行：

```sh
export INFRAPRO_CONFIG=/absolute/path/infrapro.yaml
pnpm install --frozen-lockfile
pnpm infrapro database migrate
pnpm infrapro access sync
pnpm infrapro access check
pnpm infrapro monitoring storage init
pnpm infrapro monitoring derived check
pnpm infrapro account bootstrap
```

`database migrate`应用至当前迁移版本；`storage init`同时准备原始及派生布局。`derived check`应返回`state: passed`及布局／引擎描述。首次账号初始化必须在交互终端填写用户名、显示名和密码；已初始化环境不能再次bootstrap。随后按下方启动API、前端和worker，登录后建立租户、工程资源及授权。使用现有本机环境时应先确认配置指向，不能将此流程当作重置现有数据库的命令。

### 从基础监测v12升级

1. 使用原版本CLI和原配置生成独立完整备份，保留原可执行文件、配置和备份清单hash。确认原始文件、两个CH副本和备份对象齐全。
2. 停止旧API与worker写入；切换到本轮同一源码构建的API／worker／CLI。保持数据库、账号、密钥、对象bucket与物理路由配置不变。
3. 运行`database migrate`、`access sync`、`access check`和`monitoring storage init`。旧通道迁移为direct；新派生表从空开始。迁移不会把既有自定义角色扩大为派生管理员，项目创建委托和输入数据授权也需分别显式配置。
4. 运行`monitoring derived check`、`monitoring derived reconcile --tenant TENANT_ID`，再启动API和worker。抽查旧设备绑定、直接通道、项目资源授权、已有导入、撤销历史和原始统计；然后建立一条派生通道验证新增能力。
5. 发现问题时保留日志和失败收据。已有正式派生证据的迁移不支持向下删除；恢复原版本应将升级前备份恢复到独立空目标，并由维护人员切换连接。不能让旧程序继续写新版本控制库；就绪检查会拒绝该组合。

已有归档项目或停用租户时，首次派生权限发布只允许完整、从未登记过的项目派生权限进入尚未使用派生功能的范围；不会改变项目状态、成员绑定、自定义角色或资源与数据授权。已有派生通道、分析配置或派生资源能力时仍拒绝此例外，后续扩权继续受冻结保护。

持久本机监测环境使用每副本 2 GiB 容器上限、1.5 GB ClickHouse 服务预算，并停用高频内部指标和堆栈采样，保留查询与错误日志。旧卷中已经积累的内部采样表仍会自行合并；若它们触发内存不足，应先定位具体系统表并保留日志，再限制这些已停用采样表的后台合并，不能删除监测业务表或验收数据卷。容器健康后还需等待 `monitoring derived check` 通过，才启动 worker。


在已经完成数据库迁移和物理存储初始化的环境中：

```sh
pnpm infrapro monitoring derived check
pnpm dev
go run ./services/api/cmd/monitoring-worker
```

前端地址以当前启动终端输出为准；普通开发默认 5173。`check` 检查当前迁移、权限目录、原始与派生布局、引擎及变化日志。缺少派生布局时，由维护人员按监测存储初始化流程准备；启用、恢复和发布配置会被就绪门禁阻止。普通只读检查不会自动升级数据库或修改物理表。

`pnpm dev`会持续占用终端；独立worker命令在另一个终端运行，并设置同一个`INFRAPRO_CONFIG`。生产构建使用`pnpm build`，部署生成的API、worker与CLI；不要混用不同构建的引擎。仅启动API不会自动执行共享计算队列。

```sh
pnpm infrapro monitoring derived status --tenant TENANT_ID
pnpm infrapro monitoring derived reconcile --tenant TENANT_ID
pnpm infrapro monitoring derived recovery --tenant TENANT_ID
```

这些命令只读。状态按有界类型汇总队列、dirty、消费者位置差、租约、实际发布延迟、attempt、完整性和回收状态。不要将物理字节、重复尝试行或历史修订行当作逻辑当前结果数。reconcile 发现问题返回失败；不会修补或删除证据。

运维日志 `monitoring.operation` 的 `phase_ms` 为本次执行各阶段累计耗时；其中`read_qualify/read_current/read_payload/read_recheck`是依赖解析、读取前资格、载荷及返回前复核的子阶段，与所在任务阶段有重叠，不能相加当作总耗时；`input_rows/input_encoded_bytes` 是实际读取工作量，包含窗口前缀及分块重读。`computed_output_rows/calculation_states` 包括尚未发布的计算结果；正式是否可见仍以发布代次和任务状态为准。`process_heap_peak_bytes` 按阶段和共享心跳采样，表示所在进程；`temporary_peak_bytes` 记录已观测排序或结果临时载荷峰值。任务日志含 task/run/generation、source position、图/配置修订和 fence，可与 API trace 关联，不记录输入值、密钥或对象访问地址。

`reconcile` 的载荷字节分为 `current_referenced_payload_bytes`（当前根引用的完整块）、`historical_only_payload_bytes`（仅保留于历史的派生块）、`artifact_payload_bytes`（固定分析成果）；三者合计为 `payload_bytes`。同一物理块仍被当前片段引用时整块只计入当前成本。它们是规范载荷的编码字节，不是压缩后的 CH 多副本磁盘总量，部署还应采集容器/主机磁盘与 S3 实际占用。

每日共享 verify 任务核对已发布结果。确实缺失或损坏的结果标记为不可读取，超时或临时断连保持可重试。核对成功后按配置清理已完成运行的临时排序段、不被正式清单采用的 attempt、临时检查点、未被启用委托引用的过期试算以及过期下载文件。正式结果、规则、采用依据和历史根长期保留；排队、运行、等待重试或需要处理的任务检查点保留。排序目录通过进程锁保护，超过 TTL 的活跃任务不会被当作孤儿清除。

业务 CLI 通过真实登录和同一 HTTP 权限、预览、审计执行：

pnpm infrapro monitoring derived login --url http://127.0.0.1:5173 --username USER --session-file /absolute/path/session.json

登录密码在终端交互输入；会话写入新的 0600 文件。不要把会话文件提交到仓库。项目操作加 `--project PROJECT_ID`，不能省略项目参数来绕过项目授权。resume/backfill 同样先预览后明确提交；完整参数以 `monitoring derived --help` 为准。`--request-id` 可用于请求重试，提交结果不明时先核对原请求，不要无条件创建新业务任务。

独立备份、恢复到隔离目标、验证及开放写入沿用[监测维护说明](monitoring-data.md)。派生快照包含固定配置、引擎／编译版本、构建摘要和算法夹具。恢复检查包括当前与历史根、分析成果、原始采用、上游和基准。无法执行对应旧引擎时明确报告，不能按新引擎悄悄替代。开放写入是独立维护步骤，只有验证通过后执行。

性能、压力和长时稳定性验证使用以下专项入口，功能检查不能代替这些容量与稳定性检查：

```sh
pnpm test:derived:pipeline
pnpm test:derived:soak
```

真实 PG／CH／S3 检查使用一次性实验室，物理测试串行运行；具体已执行命令与结果以[本机工程环境与人工验收](local-environment.md)为准。`pipeline`包含交互目标、四种各百万输入的真实链路及最大活动窗口；`soak`使用真实墙钟，至少需要2小时混合负载和24小时观察，另加准备与最终核对时间。短测选项仅用于接缝检查，不能代替完整观察。运行时保持主机唤醒，不与其他物理测试或验收会话共用实验室。纯计算器的百万输入测试不能代替正式导入、存储、任务、查询和导出的 DP-0。独立恢复、完整百万链路、混合负载、持续观察及人工验收分别记录，不能互相替代。
