## 如果将自动切换作为部署要求

推荐评估 PostgreSQL＋Patroni，并为其提供独立管理的三节点仲裁服务，例如 etcd。仲裁节点与 PostgreSQL 数据副本是两类组件；三个仲裁节点不能替代第三份数据库数据。该方向尚未安装，增加第三个数据副本也不视为已确定的主机安排。

完整机制需覆盖以下链路：

1. 持续检测数据库健康、复制进度、当前主角色和仲裁多数派，区分数据库进程故障、整机故障、网络隔离与短暂超时。
2. 旧主失去资格时停止接受写入；结合已验证的 watchdog／fencing 保证失联旧主不能继续写入。仲裁不可用时采用明确的拒绝提升策略，防止两台都当主库。
3. 仅将满足所选复制／持久性条件的备库提升为主库，滞后或不合格候选不能强行提升。
4. 应用连接入口根据当前主角色路由，失效连接重建；验证 API 和全部 worker 都能重新连接。在途事务可能结果不确定，不能将任意写请求无条件重试。
5. 原主恢复后按备库重新加入，必要时 rewind 或重建并追平；不自动争抢主角色。切换事件、延迟与恢复状态对运维可见。

PostgreSQL 本身不提供完整的故障检测／自动切换控制软件。Patroni 可承担角色管理，但仍要验证仲裁、旧主隔离、客户端入口与恢复行为，不能把安装一个服务视为完成自动切换。

## 数据保护和持续写入的取舍

| 方案 | 可以达到的目标 | 明确限制 |
|---|---|---|
| 两数据节点，异步复制及自动切换 | 合格备库可自动接管，恢复数据库写入 | 主库故障可能丢失最近尚未复制的已提交事务；延迟限制不能直接证明零丢失 |
| 两数据节点，严格同步复制 | 正常成功提交需在主库及同步备库持久保存 | 只剩一个节点时无法继续满足两份持久副本条件，严格模式下写入暂停；提升主角色不等于恢复写入 |
| 三数据节点，主库加两个备库，要求至少一个合格备库同步确认 | 在正确选举、隔离和独立故障域条件下，单数据节点故障后仍可保有同步副本并恢复写入 | 需要重新分配服务器内存和磁盘、限制并发并完成故障演练；不是全平台零停机或任意多机故障零丢失保证 |

只开 Patroni `synchronous_mode` 而不启用严格模式时，无合格备库阶段可能退化为单份写入，需要明确暴露这一状态。三节点方案也必须限制可能绕过同步策略的连接／事务，并区分客户端已收到成功的事务与超时、结果未知的事务。

若生产目标是“单数据库节点故障后自动恢复写入，并保护已向客户端确认的提交”，优先评估三数据节点方案；不能沿用双节点严格同步方案并同时承诺该目标。现有 151 的 16 GiB 内存还承担 CH、relay 及其独立数据库，增加业务备库前必须重算预算。

## 什么证据才算同步与切换验收通过

- **复制状态**：主库 `pg_stat_replication` 和备库 `pg_stat_wal_receiver` 持续正常；核对 streaming 与所选 sync/quorum/async 模式，观察发送、落盘和回放位置差距，监控复制槽及 WAL 占用。单次 SELECT 1、单次延迟为零或能连上端口不构成复制验证。
- **业务可见性**：持续写入带唯一编号和校验信息的受控数据，跟踪每次明确成功的提交；备库追平后核验数量与内容。对正在变化的表不能用两个不同时间点的总行数直接判定一致。
- **故障切换**：分别演练主库进程停止、数据库节点故障、网络隔离、备库失联、仲裁失去多数派。记录检测、提升、应用恢复的实测耗时和唯一可写主节点；核对切换后的全部成功提交记录，并记录结果未知事务。
- **恢复重入**：旧主恢复后只作为备库加入，复制继续追平，没有两个可写主库；再次切换或维护切换同样通过。
- **应用层**：API、全部 worker、连接池及业务幂等／恢复行为通过。需要另验 Redis、业务 S3、files 本机暂存与应用节点故障；当前应用和业务 S3 集中在 152，152 整机故障时仅切数据库不能恢复整个平台。
- **ClickHouse**：另验复制队列、只读状态、Keeper 仲裁、已发布数据完整性和故障后的查询／写入行为；PG 自动切换不会改变现有 CH 的全部副本写入约束。

未承诺具体恢复秒数、复制延迟上限或零丢失 SLA；这些必须在最终选定拓扑、持久性策略和目标负载下测量。检查过程中没有停库、制造故障、修改时间、安装软件或更改 38。
