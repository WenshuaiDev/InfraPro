## 2 规则及操作提示

本轮共 45 项平台定义权限，其中 19 项租户权限：11 项可配置业务能力，8 项当前管理员保留能力。共 8 个内置角色：2 个账号角色、6 个租户角色。普通预置租户角色可以直接绑定，也可以复制；管理员角色只能走创建租户或平台交接流程。

角色创建不会自动授权。成员加入时明确授予普通成员角色；之后可多选、撤销默认角色或清空全部角色。权限取当前租户各有效角色的并集；相同权限列出全部来源。角色停用保留绑定，但不能新增绑定；删除要求所有未撤销绑定均已解除，包括暂停成员和不可用账号。

暂停成员可预配置恢复后的职责；账号不可用时只能减绑定。成员被移除后再次加入使用新关系，仅授默认普通角色。成员管理者不能操作自己、当前管理员或配置超出其权限覆盖范围的目标。平台交接给已有有效成员时撤销其原全部角色，改授唯一管理员角色；暂停成员不能被隐式恢复。

权限修改、角色启停或删除、成员角色替换均须先预览。页面分别显示绑定数、当前有效成员数、实际增减权、恢复后影响和邀请数量。只有失去最后一个 `tenant.invitation.create` 来源，才会永久作废该成员在该租户的待领取邀请；恢复权限不会复活旧邀请。

冲突时保留草稿，点击“刷新状态并重新核对”，重新预览，再确认。密码复验后也须再次明确确认，不自动重放写入。授权提交后的新 API 请求立即按数据库判断；前端通过响应、聚焦重查及 30 秒兜底刷新更新，不承诺跨设备毫秒级推送。

## 3 人工验收准备

使用合法开户及邀请流程准备平台人员 P、租户管理员甲、普通账号乙、丙及丁。P 创建 A、B 两个租户，均指定甲；甲邀请乙加入 A、B，邀请丙加入 A，丁保持未加入。可用不同浏览器用户配置或独立隐身上下文；普通多标签共享 Cookie，只适合验证同账号并发。

原有本机数据不自动填充演示租户和成员。自动测试账号属于隔离测试环境，不是本机验收凭据。

## 4 人工验收步骤及预期

| 步骤 | 操作 | 预期结果 |
| --- | --- | --- |
| 1 就地权限说明 | 甲进入 A 的角色创建页，查看“权限说明”，搜索“邀请”，按需显示编码并展开管理员保留能力 | 可配置业务能力及保留能力以当前目录为准，均有用途、范围和风险说明；保留能力只读，没有新增权限定义入口。搜索不清空已选项，分组选择说明覆盖数量；侧栏和页面搜索没有独立租户权限目录 |
| 2 直接分配 | 在乙的成员详情选择“租户资料维护员”，先预览、填写原因并确认 | 无需复制即可使用；乙原 Cookie 的新请求可修改 A 资料，B 仍只有原权限；来源列出重复提供资料查看的所有角色 |
| 3 独立复制 | 复制“租户邀请协作员”为“A 协作”，移除撤销与重新生成权限后保存 | 新角色属于 A，基本资料显示复制来源版本，不复制绑定；授予乙后可创建普通成员邀请但不能撤销、重发 |
| 4 权限并集 | 再为乙授予另一个含邀请 create 的角色，乙邀请丁；先解绑一个 create 来源，再解绑最后一个 | 第一次不会作废邀请；第二次预览显示失效邀请，提交后丁不能领取；恢复授权不会复活链接；B 邀请不受影响 |
| 5 角色生命周期 | 给乙、丙授同一本地角色，停用；尝试删除；给新成员新增停用角色 | 停用保留绑定，实际独有权限失效，重叠权限仍有效；仍有绑定时删除受阻，停用角色不能新增绑定 |
| 6 暂停与空集合 | 暂停乙，调整其角色后恢复；再清空其全部角色 | 暂停时保留已配置角色并显示当前不生效；恢复同一关系使用新配置。清空后关系仍在，仅能看本人最小授权，资料及业务 API 拒绝，登录不补默认角色 |
| 7 历史与重入 | 移除乙后发新邀请，乙再次加入 | 新 membership_id；只授普通成员角色，旧自定义角色不恢复；旧关系及全部授予/撤销记录可查 |
| 8 名称与复制边界 | A、B 分别创建同名角色；A 再次创建同名，或使用预置名称；尝试复制管理员 | 跨租户同名允许；同租户重名及预置名称冲突拒绝。管理员不可复制、不可常规分配或解绑；空权限角色允许创建且不自动绑定 |
| 9 目标覆盖 | 仅给丙“成员管理人员”，尝试恢复/暂停具有邀请能力的乙；再补足相应邀请角色 | 不完整覆盖时 UI 给出原因、API 拒绝；覆盖完整后可操作。自己及当前管理员始终受保护 |
| 10 管理员交接 | P 交接 A 给已有多角色有效成员乙，再试向暂停成员交接 B | 预览列出接任人将被撤销的全部角色。A 复用乙关系但只保留管理员角色，甲 A 关系结束；暂停接任人被拒绝，B 不被改变 |
| 11 版本、复验 | 同账号两个窗口编辑相同角色或成员，先后提交；过期复验后再次操作 | 后提交旧版本冲突，保留草稿但须刷新、重新预览；复验成功不自动提交。取消后焦点回到触发按钮 |
| 12 隔离和审计 | 查看 A 角色和成员审计，再切 B；普通成员直接访问角色目录；平台查看预置目录 | 原因、操作者、版本、权限差异及来源可追溯，只见本租户影响；普通成员不能读完整目录；平台目录只读且无租户人员名单 |
| 13 窄屏和原流程 | 375px 与桌面、明暗主题，用键盘完成创建/授权/取消；检查登录、本人账号、平台角色、邀请和租户资料 | 主要授权操作不依赖横向表格滚动，可见标签、焦点及错误反馈；既有账号及成员流程保持 |

发布更新共享定义、直接 SQL 防护、锁超时、事务竞争和审计故障注入由验证记录提供可复现自动测试证据；不要求在人工验收库手动注入故障。

## 5 增量发布与恢复

本轮迁移为 `00005_tenant_role_authorization.sql`。对其他既有环境，先停止全部旧 API 写入，备份数据库及匹配配置，并在独立数据库实际恢复验证，使用同一版本 CLI、API 与 console：

```bash
pnpm infrapro database migrate
pnpm infrapro access sync --dry-run
pnpm infrapro access sync
pnpm infrapro access check
make dev
```

`--dry-run` 使用只读一致性快照，输出目录与预置定义差异、名称冲突、受影响租户/成员及邀请统计，不递增版本或审计。检查 `conflicts` 必须为空；若影响规模超过维护窗口，停止发布并另行安排，当前不提供跨租户批量发布调度。真实同步使用全局授权事务锁，比较数据库旧目录事实与新代码定义，原子关闭失权邀请、追加每租户审计；重复同步无版本和审计副作用。

升级保持原角色 ID、成员及绑定历史、账号、密码、会话和邀请。新预置角色不会自动绑定任何已有人员。自定义副本不跟随源角色更新；平台退役权限即使留有历史引用也不再生效，重新启用前须明确移除退役项。新预置名称与存量本地名冲突会阻止同步，不擅自改名。

迁移/目录不一致时 API 拒绝就绪；旧 API 不得继续服务新目录，不允许滚动混跑。Down 明确拒绝删除历史。优先前向修复；确需恢复时停止写入、恢复经过验证的备份及匹配程序，按既有维护入口执行：

```bash
pnpm infrapro account revoke-access --reason '备份恢复后统一撤销旧凭据'
pnpm infrapro access check
```

这会撤销旧会话、开户及重置凭据、未领取租户邀请；成员和角色关系仍保留。HTTP 隔离测试实际执行 pg_dump/pg_restore 并验证此流程；不要在本机验收库重复执行该撤销命令。
