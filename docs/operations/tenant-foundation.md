## 2 发布与恢复

1. 确认目标环境，保存 PostgreSQL 备份和旧应用版本；停止旧 API 写入。
2. 若完整平台能力仅由自定义角色提供，发布前显式给正常账号绑定内置平台管理员角色：`pnpm infrapro access recover-admin --username <用户名> --reason '租户版本发布前保障管理能力'`。此命令不恢复停用账号。
3. 使用同版本 CLI 依次 migrate → access sync → access check。新增 4 项平台权限不会自动补进自定义角色；没有完整管理能力时同步整体失败，不静默扩权。
4. 发布匹配的 API 与 console，再检查 `/readyz`。迁移版本或目录不匹配会拒绝服务。
5. 执行创建、进入、交接、原账号登录冒烟。正式部署沿用 Nginx 同源 `/console/` 前缀，例如 `/console/platform/tenants`、`/console/t/<UUID>/profile`。

本地 Compose 备份示例（输出目录应限制访问，不提交版本库）：

```bash
umask 077
mkdir -p .artifacts/backups
docker compose --env-file .env -f deploy/compose/local.yaml exec -T postgres \
  pg_dump -U infrapro -d infrapro -Fc > .artifacts/backups/pre-tenant.dump
```

本次升级前备份：`.artifacts/tenant-foundation/local-before-v3.dump`，权限 0600。已恢复到独立临时数据库，逐表核对行数与内容指纹，再验证升级、sync/check 和 `account revoke-access`，最后删除演练数据库。本地正式库只执行升级，没有执行凭据撤销。升级摘要与 SHA-256 在 `.artifacts/tenant-foundation/local-upgrade.json`。

迁移与同步失败时维持停服，先修复失败原因再重试；迁移和同步各自在事务中回滚。本轮迁移禁止 Down，不能用回退脚本删除成员历史。已写入租户数据后优先前向修复；确需从备份恢复时，停止全部写入、按[账号恢复手册](account-management.md)恢复匹配版本并执行 `account revoke-access --reason ...`，撤销备份中的旧会话、邀请和重置凭据。恢复演练没有覆盖异机灾备、生产容量或长时间恢复指标。

## 4 人工验收步骤与预期

| 步骤 | 操作 | 预期结果 |
| --- | --- | --- |
| 1 空态 | 甲、乙打开左上切换器并选择“租户”；P 打开“租户管理” | 甲乙显示“尚未加入租户，请联系平台管理人员”；平台初始无租户，个人功能仍可使用 |
| 2 建档 | P 创建 A（编号 `accept-a`），搜索甲的用户名并选择；填原因。再创建 B（`accept-b`）指定乙 | 显示名称、编号和完整管理员身份；每个租户只有一位管理员；P 的租户选择器不会自动出现 A/B |
| 3 编辑 | 甲进入 A，打开当前租户权限，再编辑名称、编号、说明并填原因；刷新 | 显示本租户的成员、租户管理员角色及权限来源（基础轮 3 项，成员轮已扩展为 11 项）；修改持久化；无需进入平台管理 |
| 4 编号历史 | 将 A 编号改成 `accept-a-new`；尝试让 B 使用 `accept-a`；再让 A 改回 | B 被明确拒绝且不显示占用者资料；A 可改回；URL 中 UUID 不变 |
| 5 隔离 | 复制 B 的租户页面 URL，在甲的浏览器直接打开。P 直接打开 A 的租户页面 | 甲不能访问 B；非成员 P 也不能进入 A，均显示“当前租户不可访问”，可重新选择租户。P 仍可通过平台治理页面管理 |
| 6 多租户 | P 将 B 交接给甲，甲不退出登录，重新打开租户选择器；分别开 A/B 两个标签 | 甲可进入 A/B，两标签名称、编号及权限来源独立。切换一个标签不改变另一个 |
| 7 草稿 | 甲在 A 打开编辑并填写未提交内容，关闭或离开；选择继续编辑/放弃；再进入 B | 继续编辑保留输入，放弃后 B 不出现 A 草稿。正在提交时离开有结果核实提示；取消浏览器请求不意味着撤销服务端操作 |
| 8 交接撤权 | P 将 A 从甲交接给乙。甲、乙保留原会话，刷新或重新聚焦；甲仍打开 B | 乙立即可以进入 A；甲的新 A 请求立即被拒绝，页面失权后清理草稿；甲在 B 的权限不受影响 |
| 9 停用联动 | P 尝试停用仍管理 B 的甲；随后先将 B 交给乙，再停用甲 | 未全部交接前提示须交接的数量，甲账号和会话不变；交接完成后可停用。账号详情的租户任职仅对同时具有账号和租户查看权限者显示 |
| 10 再次接任 | 恢复甲并重新登录，再将某租户交回甲；展开当前租户权限 | 使用新的成员关系 ID；旧成员和角色绑定保留结束历史，不重新启用 |
| 11 审计 | 分别查看平台租户详情、平台审计、租户操作记录；按事件、原因、时间筛选并翻页 | 创建、修改、交接的原因、前后值、操作者快照完整；租户仅见自身治理记录，不见 IP、UA、个人安全记录或其他租户 |
| 12 版本冲突 | 同一租户在两个有编辑权的窗口打开编辑，先后提交 | 后提交者收到版本冲突；本地输入保留。点“加载最新内容并比较”，核对后再次提交，不自动覆盖 |
| 13 复验 | 登录超过最近密码复验窗口后，提交建档、编辑或交接 | 提示当前密码；复验后保留输入，并要求再次明确提交，不自动重放 |
| 14 窄屏与键盘 | 375px 手机视口完成建档、编辑、交接；键盘 Tab/Shift+Tab、Escape 操作弹窗 | 列表改为可读卡片；主要按钮无需横向滚动；焦点进入弹窗、关闭后返回触发按钮；错误有文字定位 |
| 15 原功能 | 检查资料、改密、会话、退出、邀请、角色配置 | 既有流程仍有效；平台角色配置中没有租户管理员角色，平台角色不能包含租户权限 |

仅创建、仅编辑、仅交接权限不会隐式获得查看能力。只有创建权限时可使用创建表单并查看本次成功结果；详情/编辑/交接页面会提示还需要配套查看权限。所有接口仍独立检查对应动作，页面提示不代替后端校验。

故障注入、锁竞争、迟到请求、自动撤权和跨账号缓存清理由自动测试提供证据；人工重点验收实际流程与表达。未满足项继续在本迭代修复，用户明确确认后才将功能标记 Accepted。

## 5 应急停用验收（仅专用验收环境）

选择当前管理员甲，记录其负责的租户。普通 CLI 同样要求先交接：

```bash
pnpm infrapro account disable --username <甲用户名> --reason '验收普通停用保护'
```

预期失败，提示先交接，账号会话不变。应急停用需显式选项和原因：

```bash
pnpm infrapro account disable --username <甲用户名> --emergency --reason '验收应急停用'
```

预期甲旧会话失效；平台列表/详情显示“管理员不可用，待处理”，`/readyz` 仍成功，平台可交接。分别验证：

- **未交接先恢复**：执行 `account enable --username <甲用户名> --reason '验收恢复'`；甲重新登录后原关系恢复有效，旧会话不复活。
- **先交接再恢复**：P 将租户交给乙，再恢复甲；甲重新登录也不能进入已交接租户，乙继续管理。

若应急操作导致平台管理能力也丢失，按账号恢复流程核验身份、恢复凭据，再显式 `access recover-admin` 与 `account enable`。不重新 bootstrap，不使用 HTTP force 或代登录入口。

## 6 保留策略与边界

租户审计与账号审计共用 `audit_retention`，默认 `2160h`（90 天）。成员关系、已撤销绑定和编号归属不随审计清理删除；不得将审计描述为永久保存。

基础轮未包含的普通成员邀请和生命周期已在[成员管理迭代](tenant-membership.md)实现。当前仍不提供成员自助退出、并列管理员、自定义租户角色、租户启停/删除、项目、配额、计费或跨系统认证。尚未进行用户人工验收、生产部署、生产容量和长期稳定性验证。
