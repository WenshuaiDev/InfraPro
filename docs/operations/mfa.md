# MFA 运行、恢复与验收

实现范围和状态见[开发规格](../development/mfa-development-spec.md)及[验证账本](../verification/mfa.md)。本手册描述 schema 56 的实际行为。人工验收与生产发布分别记录。

## 使用入口

从当前 `public_console_url` 进入 `/login`、`/security`、`/platform/security-policy`、`/access/accounts`；管理员恢复链接进入 `/mfa-recovery#token=…`。部署有 `/console/` 前缀时保留该前缀。

- 不强制时，未绑定账号用密码登录；已启用账号每次新登录仍需 TOTP 或一个恢复码。
- 强制时，未绑定账号在密码通过后绑定新验证器。完成前不能访问工作空间、文件、通知或其他业务数据。
- MFA 属于全局账号，在租户、项目之间切换不重复绑定。MFA 不增加业务权限。
- 登录后启用、更换、关闭、重建恢复码、修改平台策略及管理员重置，只沿用最近五分钟的密码复验。更换时只校验**新验证器**，不要求旧 TOTP 或恢复码。
- 每次启用、更换和受控恢复生成 10 个恢复码，仅显示一次。复制、下载由用户主动点击；关闭页面后无法重新读取。恢复码与验证器分开保管。
- 强制开关由关闭变为开启后，旧密码会话失效；随后关闭强制也不能使这些旧会话恢复。已有有效 MFA 会话在原有效期内继续使用。

## 安装与升级

API 和账号维护 CLI 必须读取独立 MFA keyring。密钥文件放在仓库、Web 根目录、镜像和构建产物之外，不能复用 CSRF、Redis、数据库、诊断或机器凭证。API 启动不会自动生成或替换密钥。

首次显式生成示例（路径由部署人员选择，命令不打印密钥）：

```sh
node --input-type=module -e 'import { createMFAKeyring } from "./scripts/mfa-keyring.mjs"; createMFAKeyring(process.argv[1]);' /absolute/private/infrapro/mfa-keyring.json
```

生成器使用安全随机数和独占创建，已有文件时拒绝覆盖。运行账号须能读取该文件；目录限制访问，文件使用 `0600`。只读 `0400` 文件亦可用于运行。容器挂载前核对实际服务 UID/GID，不通过开放组或其他用户读权限解决访问问题。

配置增加：

```yaml
mfa_keyring_file: /absolute/private/infrapro/mfa-keyring.json
mfa_issuer: InfraPro
```

对应环境变量为 `INFRAPRO_MFA_KEYRING_FILE`、`INFRAPRO_MFA_ISSUER`。Issuer 为去掉首尾空白后的 1–64 字符，无控制字符，默认 `InfraPro`；它与账号标签进入本机生成的二维码，不访问外部二维码服务。

keyring 为严格 JSON：`format_version: 1`、`active_key_id` 和 `keys` 数组；每项含唯一 `id` 及 `key_base64`，解码后恰为 32 字节。ID 使用 1–64 位字母、数字、下划线或短横线，最多 32 项，文件不超过 64 KiB。启动拒绝无效权限、格式、长度及不存在的 active ID。不要把真实文件内容粘贴进工单或文档。

发布顺序：

1. 备份数据库、当前配置和兼容程序；独立保管 keyring 备份，核对所有 API 节点时间同步。
2. 先隔离旧身份 API 的人员流量，分发同一 keyring。关闭旧进程自动拉起机制，避免新旧认证代码混跑。
3. 用新 CLI 执行 `infrapro database migrate`、`infrapro access sync`、`infrapro access check`。迁移默认不强制，存量及新建账号均有 `disabled` MFA 状态；旧会话标记为 password、强制代次 0。
4. 发布同一兼容版本的 API、控制台和人员 CLI。检查 `/readyz`、权限目录与接口契约。数据库引用未知 key_id、策略行缺失或账号缺状态时不能开放人员入口。
5. 验证可选登录、绑定和三种恢复路径。由平台管理员在页面决定何时开启强制；升级脚本不自动开启。

`deploy/compose/compose.yaml` 通过 `MFA_KEYRING_FILE` 只读挂载 API 与 ops，`create_host_path: false` 防止路径拼写错误生成目录。该 Compose 示例使用 HTTP；正式 HTTPS 的安全 Cookie、代理来源和证书沿用[HTTPS 手册](https-deployment.md)。`http-test.yaml` 的自动随机密钥仅用于可销毁的隔离测试卷。

新建本机环境的 `setup:local`／`local:init` 会显式准备仓库外文件。已有 `.env.local` 或本机运行配置不会被静默改写；维护者须保留现有密码和前缀，只补上述 MFA 配置，并在停止旧 API 后迁移与同步。不得重新 bootstrap 已初始化系统。

采集、监测、空间 worker 和独立大屏运行进程不装配人员解密服务，无需该 keyring；人员大屏仍从数据库检查原人员会话的 MFA 证明。通知、文件、任务、解析、接入中继和机器终端维持原机器权限。独立诊断账号体系不受全局 MFA 开关控制。

## 日常故障与秘密响应

TOTP 固定为 HMAC-SHA-1、6 位、30 秒、160 位随机因素，前后各允许一步。数据库保存已消费的最大时间步；相同码的消费不能因重启、跨 API 或时钟回拨再次成功。码无效时先核对设备时间；不放宽窗口或清除防重放记录。

五次错误会结束挑战，并进入账号级冷却；新建挑战、换浏览器或换 API 不清计数。冷却从 30 秒递增，最大 15 分钟，同时保留 Redis 共享 IP 和账号请求预算，换来源 IP 不能绕过账号限制。429 响应带 `Retry-After`，页面显示等待时间。避免把清空失败计数作为人工解锁办法，丢失因素应走恢复。

数据库、Redis 和密钥故障返回不可用，不按“未启用”放行。排查连接、权限、完整 keyring、数据库迁移版本和 readiness；日志仅用请求/操作 ID、错误类别和计数定位，不采集 OTP、恢复码、二维码 URI、请求正文或认证 Cookie。

响应丢失时先重新读取当前状态或核对原命令收据。策略保存、关闭、重建和管理员重置使用幂等命令；收据不保存恢复码或恢复链接。绑定确认只成功一次，重复请求不回传原秘密。丢失恢复码展示时，重新登录并按密码复验主动重建；丢失管理员恢复链接时核对重置状态，再主动签发新授权，旧授权立即失效。前端不会自动重做这些写入。

绑定后 Redis 交付失败时，已提交的因素保留，未交付会话被撤销；重新用密码和新因素登录。不要把“浏览器未收到成功”解释为因素一定未启用。

API 每 60 秒执行有界挑战清理，每批最多 500 条：清空到期临时密文，终态超过 24 小时删除。每 60 秒记录 `mfa authentication counts`，仅包含保留窗口内失败数与待完成挑战数；这些是聚合诊断值，不含账号/IP 等标签。

## 三种恢复

### 验证器丢失但恢复码可用

正常输入密码，在第二步选择“使用恢复码”。成功后该码永久消费。进入账号安全更换验证器，只需既有密码复验和新验证器动态码；新因素提交后旧因素、旧码组、旧会话和未完成挑战失效。

### 平台管理员重置

管理员须拥有 `platform.account.mfa.reset`；列表详情读取另外需要 `platform.account.read`。在账号详情读取 MFA 状态和版本，确认目标、原因和影响后重置。此操作不能用来重置管理员自己，不能查看目标因素或恢复码，也不修改账号启停状态、角色或租户关系。

结果中的专用恢复链接只显示一次，有效期 30 分钟。经已确认的安全渠道交给目标用户。目标必须输入自己的密码、认领该授权，再绑定新验证器；平台处于可选模式也不能跳过。新授权取代旧授权，错误账号、过期和重复认领均拒绝。停用账号仍不能登录。

恢复 fragment 在页面初始化时从地址栏移除，只保存在该页面的内存中，与邀请、密码恢复及租户邀请凭证用途隔离。刷新可能需要重新打开原链接；不要把链接放入查询参数。

### 唯一管理员维护恢复

在具有受控数据库维护权限、完整配置和 keyring 的主机终端执行：

```sh
infrapro account mfa-reset --username <目标用户名> --reason <核验与恢复原因> --operator <维护员标识>
```

命令要求输入和输出均为交互终端，拒绝重定向；恢复授权只输出一次，并记录维护原因和操作者。命令不关闭全局策略，也不直接建立业务会话。随后通过页面输入目标账号密码、认领授权并重新绑定。不得把 TOTP、恢复码或链接作为命令行参数、环境变量或 shell 历史记录。

## 人员 CLI

现有 `monitoring`、`tasks`、`files` 等人员 CLI 共用 HTTP 登录客户端。例如：

```sh
infrapro monitoring auth login --url https://console.example.com --username <用户名> --session-file /absolute/private/person-session.json
```

密码和第二因素在终端隐藏输入。密码通过返回 202 时继续选择 TOTP 或恢复码；只有 `authenticated` 且收到正式 Cookie 才独占写入 `0600` 会话文件。CLI 不存挑战 Cookie，不覆盖已有文件。收到绑定/管理员恢复要求时取消临时资格并退出，先在浏览器完成绑定，再运行 CLI 登录。旧文件仍受服务器当前策略、因素版本和强制代次约束。

## 密钥轮换

1. 在受控私有文件中生成新的 32 字节密钥和独立 key_id。先将新旧密钥都分发到所有身份节点，active 暂时保持旧 ID；逐节点重启并验证 readiness。
2. 所有节点都能解密新 ID 后，将 active 切换到新 ID，再逐节点重启。全部仍保留旧解密密钥；该程序不会热加载私有文件。
3. 执行 `infrapro account mfa-rotate`。每事务最多锁 100 个账号，各账号最多处理 500 个挑战；提交后可中断重跑。因素版本、恢复码代次和 TOTP 防重放状态不改变。
4. 执行 `infrapro account mfa-keys`，确认所有仍保存的密文只引用预期 key_id；输出仅 ID 和数量。等待旧挑战清理并复查后，才能移除不再引用的密钥。
5. 核对独立历史备份的解密需要和保留策略。当前数据库零引用不表示旧备份不需要旧密钥。

缺旧 key_id 时 readiness 拒绝。先恢复正确密钥，不能以删除因素行或把账号设为 disabled 解决。无法恢复可信密钥时保持人员入口关闭，执行受控恢复和重新绑定。

## 数据库恢复与回滚

schema 56 禁止 Down。不能把程序回滚到不认识 MFA 的旧 API 后继续接受人员流量，使用兼容当前认证数据的修复版本。

时间点恢复前停止 API、相关写入任务及旧节点。恢复 PG 与独立密钥材料后，开放入口前运行：

```sh
infrapro account revoke-access --reason <备份恢复批次与原因>
infrapro access check
infrapro account mfa-keys
```

该恢复入口保守处理不可信的历史安全状态：递增认证版本及强制代次，强制 MFA，所有账号进入 `reset_required`；撤销会话、登录/自助挑战、管理员授权和全部恢复码，清除因素及临时密文，并失效 Redis。账号启停、角色、租户/项目关系保留。即使备份把已使用恢复码还原为未用、把旧验证器还原、把强制策略还原为关闭，也不能据此恢复访问。

先用维护 CLI 恢复管理员，再逐账号核验并受控重新绑定。只能在核对可信最新策略记录后由完整登录的管理员决定调整全局策略。该选择优先保护未知影响范围，恢复成本是所有人员重新绑定；不自动推断哪些历史账号曾未启用。

## 隔离验收环境

在本 checkout 运行 `pnpm mfa:lab`。脚本使用测试 PG 的随机 schema、独立 Redis 前缀、随机端口和仓库外临时 keyring；启动两个 API、控制台、运行壳、包检查与通知 worker，以及一份持续连接的人员大屏。启动还自验 U3 的同一因素跨两个 API、两个租户和项目可用且不会扩大业务权限，再恢复其初始未绑定状态。停止脚本会关闭进程、删除临时私有资料及 schema。测试依赖容器保留供其他回归使用。

入口及私有文件路径记录在 `.artifacts/mfa/manual/<时间>/session.json`；该索引不含密码、因素或 bearer URL。`credentials_file` 指向仓库外 `0600` 文件，含以下随机密码，`operator_config` 供仅此环境的维护 CLI 使用。

| 账号 | 初始资格 |
| --- | --- |
| P1 | 未绑定的平台管理员 |
| P2 | 已绑定的平台管理员 |
| P3 | 只读平台策略与审计 |
| TA | 租户 A/B 管理员、项目管理员、人员大屏会话主体 |
| U1 / U2 | 租户 A 普通成员，分别未绑定/已绑定 |
| U3 | 同时属于 A/B，并加入 A 的项目 |
| U4 | 无租户的账号 |
| U5 | 停用且已绑定的账号，用于验证重置不会恢复账号 |
| U6 | 未配置可选个人角色的账号 |

P2、U2、U5 的初始合成因素与恢复码不落盘。人工首次使用 P2/U2 时由 P1 重置，目标用真实兼容验证器扫码重新绑定；U5 重置后仍不能登录。自动测试另外覆盖其初始 enabled 状态。人员大屏入口及正在维持的会话 ID 位于索引，强制切换会终止这份会话。手工登录 TA 后重新打开该大屏可创建新的受控会话。

按[验收账本](../verification/mfa.md)执行：可选绑定与登录 → 登录后维护 → P1 开启强制与旧会话撤销 → U3 跨空间及 U6 权限 → 关闭强制 → 恢复码 → 管理员恢复 → 唯一管理员 CLI → 人员大屏与故障恢复 → 审计。实际手机扫码、生产时间同步、生产密钥分发及跨物理主机部署须单独人工确认。
